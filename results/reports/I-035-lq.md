# I-035 — the load queue and store-to-load forwarding

Work package I-035. Case `CASE=lsu.byte_forwarding`.

A load is the only instruction whose value depends on what every *earlier*
instruction did, because a store that has executed but has not left the store
queue still holds the architecturally newest value of its bytes. This package is
the structure that decides, **byte by byte**, whether a load's byte comes from
the most recent **older** store that covers it or from memory — and the card's
two Fail modes are exactly the two ways that decision can be wrong: comparing
aligned words instead of byte ranges, and forwarding a store the load has not yet
reached in program order.

## 1. The contract, and the interface decisions this package owns

The module header is the contract; this section is the part a reader of the
report needs to judge the checks.

**The three card inputs, each one expression.**

1. *Byte overlap.* Coverage is a byte range test —
   `store_addr <= x < store_addr + size_bytes(store_size)` — not a word match.
   `MOSAIC_LQ_MUTANT_ALIGNED_WORD_ONLY` replaces it with the aligned-doubleword
   comparison (`x[63:3] == store_addr[63:3]`) and the case catches it in the
   `wide` phase on the very first spanning load.

2. *The youngest older store.* The card's ordering input has no home in the
   memory system yet, so this package defines one: a store entry is older than
   the load when its identity precedes the load's. `mosaic_rob` advances
   `rob_gen` **once per allocation** (`gen_counter`, mosaic_rob), so two live
   identities are ordered by the generation distance modulo `2**ROB_GEN_W`, and
   two uops of one macro by `uop_index`. The ROB's own contract — rob_generation
   modulus 128 against at most 64 live entries — is what makes the
   half-modulus comparison exact; the module relies on it and the case asserts it
   (see §4, the `seq-window` guard). The search runs oldest-first and lets the
   last match win, so it selects the youngest older covering store.
   `MOSAIC_LQ_MUTANT_YOUNGER_FORWARDS` drops the `older` conjunct, and the
   `youngest` phase catches it forwarding a store the load has not reached.

3. *A store whose address is not known.* The store queue exports exactly this as
   `fwd_blocked_o` ("some resident entry has no address yet"), and it is taken
   whole as a whole-load block: while it is high the load is not completed, it is
   **replayed** (the endpoint's response is discarded and the load re-issued),
   and the replay is counted. The card's conservative baseline is "a load waits
   for all relevant older store addresses to be known"; the store queue's flag is
   coarser (it covers younger entries too) and taking the coarser flag is the
   safe direction. `MOSAIC_LQ_MUTANT_IGNORE_BLOCK` drops it.

   A second, narrower block is required for correctness and is *not* the card's
   rule: a store whose address **is** known, whose range covers a load byte, and
   whose **data** has not been captured. It is not a forwarding source (nothing
   to forward) and memory is not a source either (the store will write different
   bytes), so the load waits for it exactly as it waits for an unknown address.
   `architecture-review.md` §7 names "address ready but data not ready" as a case
   forwarding must cover. It is exercised by the soak and by the module's own
   expression, not by a separate directed phase.

**The store-side interface — and the one place the query port is not enough.**

The card requires this module to consume the store queue's forwarding query, and
it does: the load queue drives `fwd_query_addr_i`/`fwd_query_size_i` with the
head load's address and size every cycle, takes `fwd_blocked_o` as the
unknown-address policy above, and **cross-checks** `fwd_valid_o`/`fwd_data_o`
against the same rule applied to the store queue's exported entries. That check
runs every cycle of every phase and is exported as `o_query_mismatch_ctr`; it is
zero for the whole run (the case fails if it is not).

The byte-level *selection*, however, cannot be made through that port, and
saying so is part of the contract rather than an omission:

* `fwd_valid_o` answers only for a range that **one** store fully contains. A
  load spanning two stores — the card's "partial overlap, both directions"
  coverage — is never fully contained by any single store, so the port answers
  "no" and a consumer trusting it would take every byte from memory. Partial
  coverage is answerable only by asking about sub-ranges, and the port takes one
  query per cycle.
* The port's rule is "the youngest **resident** entry". The store queue cannot
  know where the load sits in program order — its header says so explicitly —
  so its answer includes stores *younger* than the load, which this module must
  not forward from. Filtering them out needs the entries' identities, which the
  query does not return.

So the byte-level search is made over the store queue's exported entry view
(`o_entry_pay` → `sq_entry_pay_i`, `o_count` → `sq_count_i`), which carries each
entry's address, size, data, both readiness bits and its identity — the five
things the youngest-older-per-byte rule needs. That is the store queue's
*observation* port, and its header says a functional consumer has no business
reading it; the sentence is about the store path ("the drain port is the
interface"). For the load path there is no other port carrying program order, and
building a second copy of the store queue inside this one would be worse. **This
is the interface tension this package records rather than hides**: the query port
is the source of the blocking policy and is verified against the entry view every
cycle; the entry view is the source of the per-byte selection. If the store queue
later grows a query that carries program order (for instance one that takes the
load's identity), the entry view can be dropped without changing this module's
rule.

**What is deliberately NOT here.**

* **Speculative disambiguation and violation replay** are I-036
  (`lsu.late_alias_replay`). A load here never passes an older store whose address
  is unknown; it waits. There is therefore no "executed too early" state, no
  dependence-violation detector and no replay of younger work. The replay this
  module implements is the narrower one the card names: re-issuing a load whose
  bytes were not all available once the block lifts.
* **FENCE / FENCE.I ordering** is I-037. This module knows nothing about fences.
* **Multiple outstanding transactions.** `mosaic_lsu_endpoint` holds one
  transaction at a time and this queue issues one load at a time, so completion
  is in order and there is no reorder buffer. I-043's nonblocking path changes
  that, and the exactly-once argument for issuing would have to be re-made.
* **Faults are reported, not taken.** A fault in the endpoint's response is
  carried to the result port with its cause and `tval`; the architectural trap
  decision belongs to the ROB/retire path.

**The result and the merge.** The merged value is built in the *load's* byte
order (byte `i` at bits `8i..8i+7`): a byte an older covering store owns comes
from that store's payload at its offset inside the store, and every other byte
comes from the endpoint's response, whose low bytes are the memory bytes at
`load_addr .. load_addr+n-1` in that same order (`mosaic_lsu_endpoint` extracts by
shifting the lane-aligned doubleword down to lane 0). The merged word is then
sign- or zero-extended by size, exactly as the endpoint extends a pure memory
value. `result_fwd_mask_o` reports, per byte, which of the two it came from — the
card asks for that indication and the case checks it byte by byte.
`MOSAIC_LQ_MUTANT_MEMORY_OVER_STORE` sets every byte to the memory source and is
caught in the `narrow` phase's first load.

**One outstanding load, one result slot.** The head is offered while nothing is
in flight and no result is pending, and `o_alloc_ctr == o_done_ctr + o_count` is
asserted every cycle. `MOSAIC_LQ_MUTANT_STALE_FORWARD` latches the forwarded
bytes when the load is issued and reuses them at completion instead of reading
the store queue as it stands then; the `unknown` phase catches it missing a store
whose address resolves in between.

## 2. The harness, the two-snapshot rule, and the shadows

`Bench::Cycle()` drives the inputs with the clock low, evaluates, and reads
**one** pre-edge snapshot of every DUT output. That snapshot — and nothing read
after the edge — is used by the per-cycle checks and by the shadow update, so a
value presented in cycle *N* is never mixed with the state that exists after
edge *N*. The driver models the load queue's edge explicitly (issue on
`o_lq_req_valid && o_lq_ep_req_ready`, response on `o_lq_ep_rsp_valid`, completion
on a response with the block clear), so its shadow is the queue's registered
state rather than a guess, and the store queue's edge is modelled the same way
(allocation, fill, commit watermark, squash region, drain).

**Two shadows.** The load-queue shadow is an ordered `std::vector<LqEnt>`; the
store-queue shadow is an ordered `std::vector<SqEnt>`. Each carries a
**program-order sequence number**, assigned at construction and derived the way
`mosaic_rob` derives an identity (`rob_gen` advances once per allocation,
`rob_index` is the allocation pointer). Both are compared field by field against
the DUTs' exported entry vectors **every cycle**, so a drift in either shadow is
caught rather than silently changing the expectation.

**The expectation is the card's rule, from the driver's own order.** For the load
at the head, byte `i`'s source is the youngest store whose sequence number is
*smaller* (older) and whose byte range covers `load_addr + i`; otherwise memory.
The comparison is the *driver's* order, not the RTL's generation arithmetic, so a
defect in that arithmetic shows up as a divergence. The memory byte is the
driver's own expected memory, written only where the driver expects a committed
store to have drained.

**The memory model** is a 64 KiB byte-addressed region at `0x8000_0000` behind
the two endpoint instances, with two independent ports over one address space and
per-cycle request back-pressure and latency. It does **not** check alignment:
that policy lives in `mosaic_lsu_endpoint`. A separate `exp_mem_` is updated
from the driver's expectation of each drained store and compared byte for byte
at the end of every phase.

## 3. What is checked on every cycle of every phase

1. `o_lq_count`, the occupancy bitmap and every field of every load-queue entry
   (identity, base, immediate, size, signedness), position by position.
2. `alloc_ready_o` is exactly "the shadow has room".
3. **The offer**: `o_lq_req_valid` is high exactly when a head load exists, none
   is in flight and no result is pending, and its payload names that head.
4. **The result**: when presented, identity, forward mask, fault and value match
   the expectation computed at the completion edge — the mask byte by byte, so a
   byte taken from the wrong source is a named failure rather than a value that
   happens to coincide.
5. The registered counters against the driver's tallies and the conservation
   identity `o_alloc_ctr == o_done_ctr + o_count`.
6. The store queue's entries against the driver's own store list, so the
   forwarding expectation rests on a verified store list.
7. **The store queue's forwarding query** against its rule applied to those
   entries — `fwd_valid_o`, `fwd_data_o` and `fwd_blocked_o`, for the address and
   size the load queue actually drove. Both views of the same fact are therefore
   checked against each other; `o_lq_query_mismatch_ctr` must be zero.
8. The load endpoint's memory request belongs to the load in flight (same
   address, same size, never a store).
9. The store queue's drain offer is position 0 and carries its payload.
10. The live program-order span is inside the window the generation field can
    order (below 64 allocations), so the RTL's half-modulus comparison is never
    ambiguous *in the scenario being tested*.

## 7. Defects found

**In the RTL: none found by this case** — but two design points were settled
while writing it and are recorded here rather than left implicit:

* The unknown-address policy is the store queue's `fwd_blocked_o`, which is
  *any* resident entry without an address, not only the older ones. That is
  coarser than the card's "relevant older store addresses" and is the safe
  direction; the module header says so, and the finer rule belongs to I-036,
  which will need it to speculate past unknown older stores rather than wait.
* The "address known, data not captured" block is not the card's rule but is
  required for correctness (a covering store with no data is neither a
  forwarding source nor a reason to trust memory). It is implemented and
  exercised by the soak.

**In the testbench: six, all mine, all found by a check rather than by
inspection.** They are worth recording because each is a way a case can pass
while proving nothing:

1. **Misaligned loads in the `narrow` phase.** The profile traps a misaligned
   access, so a halfword at an odd offset never reaches memory and never
   forwards; the phase was generating them and the forwarding expectation was
   wrong for them. The phase now walks only legal offsets for each size, and
   `NewLoad` marks any trapping address as an expected trap so the expectation
   cannot silently disagree with the endpoint's policy again.
2. **The identity sequence was recomputed at the edge instead of carried from
   construction.** A store and a load allocated in the same cycle swapped their
   program order, which the age filter would faithfully (and wrongly) apply. The
   stimulus now carries the sequence number the entry was constructed with.
3. **The younger-store test proved nothing.** The load's address was also covered
   by the three older stores, so it forwarded from the youngest *older* store and
   the younger store's presence changed nothing. It now uses an address no older
   store covers, so any forwarded byte could only have come from the younger
   store.
4. **The drain phase stopped one step too early.** Its loop exited as soon as the
   store queue emptied, before the store had made it through the endpoint to
   memory, so the memory check ran against a write that had not happened yet.
5. **The soak forwarded three bytes in three thousand cycles.** It squashed the
   whole store queue often, so a load almost never had an older store left to
   forward from — every load took memory and the "random" phase exercised one
   half of the rule. It now squashes rarely-as-a-whole and often-as-a-window,
   which keeps residents long enough to forward from *and* exercises the store
   queue's region rule.
6. **The driver's program-order window outgrew the generation field.** With a
   deep load backlog the live span reached 64 allocations, where the half-modulus
   comparison is ambiguous; three seeds failed on the guard that now names it.
   The soak keeps the load queue shallow and resets the sequence between epochs,
   and the guard is a standing invariant rather than a soak detail.

The first five would each have let the case pass; the sixth would have let it
pass on some seeds and failed on others, which is worse.

## 8. NOT verified

* **No integration.** The load queue is exercised against `mosaic_store_queue`,
  two `mosaic_lsu_endpoint` instances and a C++ memory model, not against the
  core. Nothing here shows that `mosaic_dispatch` allocates loads into it in
  program order, that the identity it is handed is the same one the ROB retires,
  or that the store queue's `o_entry_pay` is what a core would wire to it.
  Those are wiring facts and the case cannot see them.
* **The entry-view interface is a contract this package chose.** The store
  queue's header calls `o_entry_pay` an observation port; this module reads it
  functionally because the forwarding query cannot express program order (§1).
  If the store queue's layout changes, this module's decode must change with it —
  the wrapper's geometry check makes a width change a build-time failure, but a
  *re-ordering* of the fields would not be caught by that check alone. The
  per-cycle entry comparison against the driver's model would catch it in the
  case, but not in the core.
* **Only one load in flight.** The endpoint holds one transaction and this queue
  issues one load at a time, so the result path is in order by construction.
  I-043's nonblocking memory path would change the number of loads in flight and
  this queue's exactly-once argument with it.
* **No FENCE, no speculation, no MMIO.** Fences are I-037; speculative
  disambiguation and violation replay are I-036; MMIO exactly-once is I-038. The
  memory behind the endpoint is a `std::vector<uint8_t>`.
* **The soak's store traffic never drains.** Committed stores and their memory
  writes are exercised by the `drain` phase, in isolation; the soak uses
  whole-queue and windowed squashes to free the store queue precisely so that the
  load's memory bytes are a stable pattern. A soak that also drained would need
  the driver to model the endpoint's read/write interleaving to be independent of
  the DUT, which is not worth the loss of clarity here.
* **One geometry.** `MOSAIC_LQ_ENTRIES = 8`, `MOSAIC_SQ_ENTRIES = 8`,
  `XLEN = 64`, one hart. The RTL is parameterised from the generated packages
  and has an elaboration guard for a vacuous geometry, but no other geometry was
  elaborated.
* **Simulation only**; no synthesis or Yosys run covers the new files (they obey
  the no-assignment-pattern rule and use `logic`, so they are parseable there,
  but that was not exercised).
* **The event trace is the counters and the run log.** There is no separate
  waveform or event file.
