# V-043 — the applicable ACT4 suite on the integrated out-of-order core

**Verdict: the runner is delivered and the suite executes; 122 of 127 applicable
ELFs pass and 5 fail. The five failures are recorded as findings, so the package
is not "all applicable ACTs pass".**

- **DUT**: `mosaic_core_tb` — the integrated out-of-order core (fetch → decode →
  dispatch → two clusters → WB arbiter → ROB → retire → commit), **not** the
  bring-up core. The pre-existing `tools/run_act_dut.py` drove the bring-up core;
  this work replaces it with `CASE=core.act_dut` on `mosaic_core_tb` at profile
  **p1**.
- **Revision**: repository `8e2d1c4` (includes EX-034's IALIGN fix `97f9463`).
  Driver binary SHA-256 `ea6d1761b7adee872bd34df48e417b8104790fb2468f074cd73e121b275c0a21`.
- **ACT4**: `riscv-arch-test` @ `96493a91448ca50780013fd892daec2c204487ba`
  (the frozen checkout), UDB + Sail 0.14.1, GCC 16.2.0 toolchain via
  `~/mosaic-ref/act4-bin`.

## 1. Where the alignment assumption lives (and what was aligned)

The card's "align UDB/sail.json/rvtest_config with the platform" is delivered as a
checked-in ACT4 configuration, **`tests/act4/mosaic-p1/`**:

| file | what it fixes |
|---|---|
| `mosaic-p1.yaml` | a UDB config declaring exactly the p1 **advertised** set (I, M, A, C, S, U, Zicsr, Zifencei, Zicntr, Zihpm, Zaamo, Zalrsc, Zca) — no F/D, no H/V, no V, no stateen. The stock `sail-rv64-max` header defines `H_SUPPORTED`, which makes the ACT4 boot prologue write hypervisor CSRs p1 does not implement. |
| `link.ld` | RAM `0x80000000` + 2 MiB, matching `config/memory/p1.json`, so an oversized image is a link error rather than a DUT load failure. |
| `rvmodel_macros.h` | DUT-specific: `RVMODEL_MTIMECMP_ADDRESS`/`RVMODEL_MTIME_ADDRESS` are deliberately **undefined** (the Sail sample's `0x02004000` lies outside p1's CLINT and made every ELF take a store access fault in the boot prologue); the HTIF `tohost`/`fromhost` exit protocol is kept exactly. |
| `sail.json` | the reference-model config the expected signatures come from. |

The p1 profile's own `test_protocol.tohost` (`0x80001000`) is **not** where ACT4
links `tohost` (the ELF's `.tohost` is chosen by the linker, and for these images
`0x80001000` falls inside `.text`). The DUT therefore does **not** key on the
profile address: `sim/unit/tb_core_act.cpp` reads the image's own `tohost` symbol
and watches the retirement stream for the committed store to it. This is the
protocol-correct choice, and it is why the ELF needs no address patching.

## 2. N closed against the generation manifest

`tools/run_act_dut.py` generates the suite with `act` (clearing the generator's
`elfs/` directory first so a stale ELF from an earlier configuration cannot
inflate N), then enumerates what the generator produced:

`generated = enumerated = run = 127`; the registered case fails if the three
numbers disagree. Every excluded suite (F/D, V, H, B, crypto, Misalign, Zcb,
Zcmop, Zicntr, Zicbom, Zicbop, Zmmul, Zicond, …) is recorded with a reason, and
the runner refuses a suite that produces no ELF and has no recorded reason.

## 3. The self-check PASS macro is calibrated, not trusted

The ELFs are `RVTEST_SELFCHECK` images: Sail 0.14.1 computed the expected
signature and the framework compiled it into the ELF's own `.data`; every
`RVTEST_SIGUPD` compares the DUT's value with that word and jumps to a failure
handler on a mismatch. The runner asserts, before any ELF runs:

- the pass string `RVCP-SUMMARY: TEST PASSED` is linked in (and `TEST SIGRUN`, the
  signature-mode banner, is not);
- `tohost`, `fromhost`, `begin_signature`, `end_signature`, `rvtest_entry_point`
  are all symbols the image carries, with a non-empty signature region;
- the exit protocol is exact: `RVMODEL_HALT_PASS` writes **1**, `RVMODEL_HALT_FAIL`
  writes **3**. (An earlier revision of the driver read bit 0 and wrongly accepted
  3 as a pass; the mutant control caught it. The rule is now `value == 1`.)

**The macro is shown to be able to fail** (controls, §5): a corrupted expected
signature word makes the DUT's own comparison fail and the ELF writes 3.

## 4. What the suite ran and what it found

**122 / 127 pass.** The five failures are real self-check mismatches, located by
running the generator's signature-mode ELF (`<name>.sig.elf`, which *stores* the
DUT's computed values) and diffing against Sail's `<name>.results`:

| ELF | DUT vs Sail | reading |
|---|---|---|
| `Zca/Zca-c.lui-00` | 51 words differ; expected `0x…5000`, got `0x…50000000` | **c.lui places its 6-bit immediate 16 bits too high** — a compressed-decode defect. |
| `Zalrsc/Zalrsc-sc.d-00`, `Zalrsc-sc.w-00` | 23 words; expected `1` (SC succeeds), got `0` | **SC returns failure where Sail expects success** — reservation lost across the harness's LR→SC window. |
| `Zihpm/Zihpm-csrrc-00`, `Zihpm-csrrs-00` | 357 words; expected `0`, got live counter values (e.g. `0xb20`), and canary slots overwritten | **the `csrrc`/`csrrs` read-modify-write of the HPM counters diverges** from the Sail reference. |

The remaining 122 ELFs pass, each ending at its own `tohost=1` after executing
its own comparators: I 51/51, M 13/13, Zicsr 6/6, Zifencei 1/1, Zaamo 18/18,
Zalrsc 2/4, Zca 31/32, Zihpm 0/2.

### Harness defects found and fixed while getting here

These were **driver** defects, not DUT defects, and each was caught by the suite
itself:

- the fetch image was keyed on 4-byte-aligned addresses, so a compressed
  instruction at a 2-mod-4 PC fetched the "unmapped" ECALL sentinel and the whole
  Zca suite ran as a stream of ECALLs;
- the fetch image was a static copy, so a `fence.i` self-modification was
  invisible to the front end (Zifencei failed); the driver now keeps one byte
  image that the data port's stores also update;
- reading fetch through the shared memory model shadowed `MOSAIC_TOHOST`
  (`0x80001000`), which lies inside these images' `.text`, so four code bytes read
  as the protocol; the driver keeps its own image instead.

## 6. Exclusions and the ledger

What this suite does **not** cover, recorded in
`config/validation/exclusion_ledger.json` (EX-012, narrowed):

- **Privileged-mode ACT4 ELFs** (`tests/priv/`): not generated by this
  configuration; the unprivileged suites exercise M-mode entry and the S-mode
  T-SBI path only incidentally.
- **F, D, V, H, B, crypto, Misalign** suites: not in the p1 profile.
- **Zicond**: the p1 profile claims it but the checkout has **no Zicond suite**,
  so no ELF exists to run.
- **Zmmul, Zicntr, Zicbom, Zicbop, CMO, Zcb, Zcmop**: claimed in
  `config/profiles/p1.json` but `tools/check_profile.py --all` reports them *not
  yet implemented* / not advertised; no ACT4 evidence exists for them here.

EX-012 is therefore **narrowed, not closed**: ACT4 now executes I, M, Zicsr,
Zifencei, Zihpm, A and C on the p1 out-of-order core, but 5 of those ELFs fail and
the Zicond/Zmmul/CMO claims still have no ACT4 evidence. `core.act_dut` is named
in the entry, and `python3 tools/check_exclusions.py` stays green.

## 7. Reproduce

```
python3 tools/run_act_dut.py --controls          # generate, build, run, control
python3 tools/run_act_dut.py --no-generate       # reuse the generated ELFs
python3 tools/run_act_dut.py --limit 5           # first five, for iteration
```

Per-ELF logs are under `results/v043/cases/<suite>/<name>/`; the machine-readable
verdicts are `results/v043/dut_results.json` and `results/v043/suite_manifest.json`;
the registered case's own record is `results/unit/core.act_dut/result.json`. The
registered run (`make unit`, no `--image`) reads
`tests/act4/mosaic-p1/elf_manifest.json` and executes the whole manifest set.
