# I-034 — the speculative store queue and store-commit authorisation

Work package I-034. Case `CASE=store.wrong_path_visibility`.

A store is the only instruction whose side effect leaves the hart, and it is the
only side effect that cannot be undone. This package is the structure that keeps
the two facts apart that decide whether it may leave: **address and data are
captured** (an observation of execution) and **the store has retired** (an
authorisation from the ROB). The card's whole point — and this case's whole point
— is that the first does not imply the second.

Files delivered:

| File | Role |
|---|---|
| `rtl/core/mosaic_store_queue.sv` | the store queue: ordered entries, address/data readiness kept apart, an in-order authorisation watermark, an in-order drain to the memory endpoint, squash of the unauthorised suffix |
| `sim/tb/mosaic_store_queue_tb.sv` | simulation wrapper; both DUTs wired the way the core will wire them (queue drain → `mosaic_lsu_endpoint`), flat driver-facing ports, geometry read back |
| `sim/unit/tb_store.cpp` | C++ driver: independent shadow queue, spec-side store rules, a byte-addressed memory model behind the endpoint, eight phases |
| `results/reports/I-034-sq.md` | this file |

`rtl/core/mosaic_lsu_endpoint.sv` was **not edited**; the case uses it as the
memory side, exactly as delivered by I-033. `tests/unit/registry.json`,
`config/**`, `config/status/**` and `results/PROGRESS.md` were not touched (see
§8 for the one registration defect found and reported rather than patched).

## 1. The contract, and the interface decisions this package owns

The module header is the contract; this section is the part a reader of the
report needs to judge the checks.

**Visibility.** `drain_req_valid_o` is high exactly when position 0 of the queue
is authorised **and** both its address and its data have been captured **and**
this cycle's squash does not withdraw it. The entry leaves the queue on the
acceptance edge and not before; the store is therefore externally visible
strictly after an authorisation, never after an execution completion. That single
expression is what `MOSAIC_SQ_MUTANT_VISIBLE_BEFORE_COMMIT` removes.

**Order and authorisation.** The queue is an ordered compacted list, position 0
oldest, and authorisation is an in-order **watermark** (`o_auth_cnt`): entries
`0..auth_cnt-1` are authorised and no others. `commit_valid_i` carries the
identity of the store the ROB is committing and is applied only when it names the
first unauthorised entry; anything else is *refused* and counted
(`o_commit_stale_ctr`). The watermark is derived from the survivors of the cycle
(entries still resident and authorised) rather than adjusted arithmetically, so a
drain, a squash and a commit in any combination cannot leave it counting an entry
that is gone.

**Squash.** The dead region is a ROB-index window: the same generation as the
flush point and an index inside `[from, tail)` computed modulo the ROB index
space, plus `squash_all_i` for a whole-queue flush. An entry in the region dies
**unless it is authorised** — a store that retired is past the point recovery may
take it back. `o_squash_spared_ctr` counts the entries the region would have
taken and the watermark spared, so that behaviour is observed on every run.

**The drain is a two-way handshake with the fault boundary.** The queue presents
`mosaic_uop_pkg::lsu_req_t` to `mosaic_lsu_endpoint`'s upstream port; the
endpoint owns the misalignment policy and the access fault, and its response
returns to the queue, which consumes it unconditionally and records the fault's
identity, cause and address. A misaligned store therefore drains (it retired) and
writes nothing (the endpoint traps it before the memory sees it). The queue pops
the entry when the **request** is accepted, which is the exactly-once rule: the
endpoint owns the transaction from there, and no state in the queue can re-issue
it.

**The interface decision the card left to this package**: how I-035's younger
load asks whether a store ahead of it has the data. The decision is a **purely
combinational query port with no handshake and no side effects**
(`fwd_query_addr_i`/`fwd_query_size_i` → `fwd_valid_o`/`fwd_data_o`/
`fwd_blocked_o`). The answer is the *youngest* resident entry with both facts
captured that **fully contains** the queried byte range, in the same
doubleword; `fwd_data_o` is that entry's data in the memory-response lane
convention (`lsu_rsp_t.data`, "the byte at `addr` is lane `addr[2:0]`"), so a
load extracts from it exactly as it extracts from memory; partial coverage is
**not** answered (byte merging stays in I-035); `fwd_blocked_o` is raised while
any resident store has no captured address, because such a store might be older
and might overlap, and the consumer must treat the answer as advisory then.

**It is exercised, not merely declared.** `PhaseForward` drives the rule directly
(whole doubleword, word, halfword, byte inside a store, a query crossing the
doubleword boundary, partial coverage, blocked by an unknown address, and
youngest-wins), and every cycle of every phase also compares both outputs against
the rule in the shadow. It carries no mutant: the visibility contract is what the
case is about and this port cannot change it. See §9 for what is still not
verified about it.

## 2. The harness, the two-snapshot rule, and the shadow

`Bench::Cycle()` drives the inputs with the clock low, evaluates, and reads **one**
snapshot of every DUT output before the edge. That snapshot — and nothing read
after the edge — is used by the per-cycle checks and by the shadow update. A
value presented in cycle *N* is never mixed with the state that exists after edge
*N*; effects of an edge are therefore asserted in the following cycle, and each
phase says so where it matters (a registered counter read in the same cycle as
the event that moves it is a testbench bug, and this one had two of the
"one cycle early" kind before it was right — §7).

The **shadow** is an independent model of the contract's prose: an ordered
`std::vector<Entry>` with per-entry `addr_valid`/`data_valid`/`authorised`, the
region rule above, and the same drain predicate. It is written from the module
header and from the RISC-V store rules, shares no code with the RTL, and is the
expectation for the drain port, the whole entry vector, the occupancy and
authorisation bitmaps, every counter and the conservation identity.

The **memory model** is a 64 KiB byte-addressed region at `0x8000_0000` behind
the endpoint, with programmable request latency, back-pressure and injectable
faults. It deliberately does **not** check alignment: that policy lives in
`mosaic_lsu_endpoint`, and a model that trapped misaligned accesses would be a
second implementation of the thing under test. The driver keeps its own
expectation memory, derives it from the sequence it drove (a store writes its
little-endian bytes at `addr..addr+size-1`, and a misaligned store writes
nothing), and compares byte for byte at the end of every phase; it also compares
its expected transaction count against the model's own accepted-request counter.

## 3. What is checked on every cycle of every phase

1. `alloc_ready_o` is exactly "the shadow has room", and a refused allocation is
   never stored (the conservation identity catches a silent drop).
2. `fill_hit_o`/`fill_stale_o` against the shadow's oldest-match rule.
3. `commit_ok_o`/`commit_stale_o` against the shadow's in-order rule.
4. **The drain offer**: `drain_req_valid_o` is high exactly when the shadow's head
   is authorised, captured and not withdrawn by this cycle's squash, and the
   payload names that entry (id, base, imm, size, store data).
5. The **whole queue state**: `o_count`, `o_auth_cnt`, the occupancy and
   authorised bitmaps, and every field of every entry (identity, base, imm, size,
   data, both validity bits); positions at or above the count must read zero.
6. The seven event counters against the driver's own tallies, which are computed
   from the rule and not read back from the DUT, and the conservation identity
   `o_alloc_ctr == o_drain_ctr + o_squash_ctr + o_count`.
7. The forwarding query against the rule (§1).
8. The memory side: no request may appear without a store the queue offered; the
   request must carry the address, size, strobes and lane-shifted data the
   specification demands for that store; and a completed store must have reached
   the memory if and only if it was not misaligned.
9. A misaligned store's report — fault counted, cause, `tval` = the address,
   identity = the store — checked one cycle after the endpoint composes it.

deleted build directory** by `tools/run_unit.py` (which wipes `obj_dir` whenever
the build command differs — the mechanism that makes a `-D` change a real
rebuild), and run with the case's own binary. The three lanes that have produced
"passing mutants" in this project are all closed here:

* the define **exists in the RTL**: `grep -n MOSAIC_SQ_MUTANT rtl/core/mosaic_store_queue.sv`
  finds each of the seven, each wrapping a single assignment or a single
  selection;
* the define **elaborates**: every mutant below built, and its binary differs
  from the shipping one;
* the define **reached the compiler**: the runner writes `build_command.txt` next

## 7. Defects found

**In the RTL: none found by this case** — but one *contract* change was made
because writing the shadow exposed a gap, and it is recorded here rather than
silently absorbed:

* The watermark was first adjusted arithmetically (`auth_cnt + 1` on a commit,
  `- 1` on a drain). The soak immediately found the case it cannot express: an
  authorisation and a squash of the same entry in one cycle left the watermark
  counting an entry that no longer existed. The ROB does not retire in a flush
  cycle (`mosaic_rob`: `retire_ack = retire_req && head_ready && !flush_valid`),
  so the combination is not expected in service — but a watermark that can point
  past the entries it counts is a latent corruption for whoever wires this next,
  and the case drives random commits and squashes. The watermark is now derived
  from the survivors of the cycle, which is the same statement as the prefix
  invariant, and the module header says so.

**In the testbench: two, both mine, both fixed, both found by the memory
comparison rather than by a signal.**

1. The model was fed the endpoint's store payload through the lane shift a second
   time (`store_data << 8*lane` applied to a payload that is already
   lane-shifted). Every directed phase passed, because every directed store
   starts at lane 0 where the shift is the identity; the soak's non-zero lanes
   exposed it. The model now writes the presented payload, and the *specification*
   of that payload is checked separately in the same cycle — which is the split
   I-033's report describes, and the one that keeps the memory's contents from
   being a restatement of the RTL.
2. The driver's expected memory took the store's byte at the *lane index*
   (`data >> 8*((addr+i)&7)`) instead of the store's byte `i` at address `addr+i`.
   This is the same class of error as (1) — the lane convention describes the
   *bus*, not the memory — and it too only showed on a non-zero lane. The DUT was
   right in both cases.

Two further testbench bugs were mechanical and are recorded for completeness
because they are the kind that makes a case pass for the wrong reason: a
post-edge shadow state compared against a pre-edge snapshot (one extra idle cycle
now separates them), and a misaligned store's fault report asserted in the cycle
the endpoint composed it rather than the cycle the queue counted it.

**Defect found in the registration, reported and not patched:**

The registry entry for `store.wrong_path_visibility` listed
`rtl = [mosaic_pkg.sv, mosaic_lsu_endpoint.sv, mosaic_store_queue.sv]`.
`mosaic_lsu_endpoint.sv` refers to `mosaic_uop_pkg::lsu_req_t`/`mem_req_t`, so
the case cannot elaborate without `rtl/core/mosaic_uop_pkg.sv` before it, which
the sibling case `lsu.size_fault_boundaries` does list. Verified directly:

```
$ verilator --lint-only ... rtl/core/mosaic_pkg.sv rtl/core/mosaic_lsu_endpoint.sv
%Error: rtl/core/mosaic_lsu_endpoint.sv:100:12: Package/class for ':: reference' not found: 'mosaic_uop_pkg'
```

The lesson is worth one line in this tree: **a case's `rtl` list is an
*elaboration dependency* list, not a "files I care about" list**, and a missing
package surfaces as a confusing `:: reference not found` in a *different* module
rather than as "your list is incomplete". The fix is one line in the entry and it
was left to the registry's owner (the integration lead added it); patching it
here would have made the next lane's entry the one that broke silently.

## 8. NOT verified

* **No integration.** The queue is exercised against `mosaic_lsu_endpoint` and a
  C++ memory model, not against the core. Nothing here shows that `mosaic_rob`
  drives `commit_valid_i` with a store's identity, that `mosaic_recovery`'s
  `o_rob_flush_from` and the ROB's allocation pointer are what this port expects,
  or that the identity the ROB retires a *macro* with is the per-store identity
  this port names. Those are wiring facts and the case cannot see them.
* **The flush point's second field does not exist yet.** `squash_tail_index_i`
  (the young window's bound) is supplied by the testbench. `mosaic_rob` does not
  expose its allocation pointer today, and the module header names that gap
  rather than papering over it with a whole-queue flush — so what is verified is
  the region rule given a window, not the production source of the window.
* **The module never sees a load or a fetched instruction**, so nothing here
  constrains I-035/I-036 beyond the query port's rule; in particular the
  `fwd_blocked_o` policy ("some resident store has no address") is a conservative
  rule this package chose and I-036 may want something finer.
* **The forwarding query is not consumed by anyone.** Its rule is checked, its
  agreement with the shadow is checked every cycle, but no load uses it, and its
  *timing* (a purely combinational answer from the entry registers) is not
  exercised against a real LQ. Treat it as a defined, tested *rule*, not as a
  proven integration interface.
* **One outstanding memory transaction.** The queue presents one store at a time
  and the endpoint accepts one at a time; I-043's nonblocking memory path would
  change how many stores are in flight, and the exactly-once argument here ("the
  entry leaves on the acceptance edge") would have to be re-made for it.
* **No caches, no MMIO, no coherence.** The memory behind the endpoint is a
  `std::vector<uint8_t>`; the wrong-path check's "zero bytes" is zero bytes in
  that model, which is the strongest statement available without a bus.
* **The event trace is the counters and the run log.** The plan's "store event
  trace" is satisfied by the per-phase counter lines and the memory comparison;
  there is no separate waveform or event file.
* **Only the p0 geometry.** `MOSAIC_SQ_ENTRIES = 8`, `XLEN = 64`, one hart. The
  RTL is parameterised from the generated packages and has an elaboration guard
  for a vacuous geometry, but no other geometry was elaborated.
* **Simulation only**; no synthesis or Yosys run covers the new files (they obey
  the no-assignment-pattern rule and use `logic`, so they are parseable there,
  but that was not exercised).
