## What the arbiter implements

`mosaic_wb_arbiter` is the single place a completion becomes architectural. Three
producers (two clusters and the shared MUL/DIV) each hold one completion in a
dedicated slot; the lowest-numbered pending slot is published each cycle. The
published completion drives, **from one decision in the same cycle**:

* the PRF write port for the destination's home bank (`tag % MOSAIC_PRF_BANKS`),
  with `wr_en` and `wr_gen_valid` set together;
* the rename writeback offer (`(tag, generation)`), whose `accepted` answer is
  what makes the write legal;
* the value-visible wakeup — `wu_valid` is exactly the write decision, and
  `wu_tag`/`wu_gen`/`wu_val` are the written identity and value, so no consumer
  can be woken for a value the register file has not taken;
* the ROB completion, which every completion owes whether or not it carries a
  destination;
* the ready-table update and the durable value stash keyed by ROB index.

The rules the case enforces, and where they come from:

1. **A completion is delayed, never dropped.** A producer that is not published
   keeps its slot until it is; `wb_ready` is low only while the slot is occupied
   *and* not being published this cycle. Two completions landing on one bank are
   serialised (the loser waits), and `o_collision_ctr` counts the delay.
2. **Only the correct producer writes a generation.** `write_ok` requires rename
   to have accepted the `(tag, generation)` (not stale, not duplicate) *and* the
   ROB to consider the identity live (not stale, not a bad uop).
3. **A consumer sees a committed value.** The wakeup, the PRF write and the
   rename offer are the same decision; `wu_valid` without the matching bank write
   is the failure.
4. **The ready table names the generation written, not the tag alone.**
5. **The counters are the contract's, not the implementation's.** `o_wr_ctr`,
   `o_pub_ctr`, `o_stale_ctr`, `o_dup_ctr`, `o_rob_*_ctr`, `o_drop_ctr`,
   `o_wide_gen_ctr`, `o_store_ctr`, `o_load_ctr` are compared every cycle against
   an independent tally.

## The independent expectation, and what it does not read

The driver is the environment, not a copy of the arbiter:

* **Rename** is modelled from its documented rule — a tag owns one generation at
  a time and a generation of a tag is written at most once while it is current;
  a different offer for the tag is *stale*, a second offer for the current
  generation is *duplicate*. Reallocation to a *different* generation starts the
  written state clean, which is what lets a numeric generation be reused after
  the allocation counter wraps.
* **The ROB** is modelled from its documented rule — an identity is live until
  its macro is discarded; a completion of a discarded identity is refused.
* **The PRF is not modelled.** Every "the value is durable" claim is checked by
  reading the value back out of the elaborated `mosaic_prf` through its read
  ports with the matching `(tag, generation)`, or — in the new phase — on the
  cycle after the wakeup.
* **The collision counter is the one DUT count the driver does not model**, and
  it says so: its value depends on how the arbiter chose to hold the pending set,
  which is implementation, not contract. It is tracked monotonically and its
  per-phase delta is asserted only where the contract names it.

The case compiles **only** `rtl/core/mosaic_wb_arbiter.sv` and
`rtl/core/mosaic_prf.sv`. It does **not** read `rtl/core/mosaic_rename.sv` or
`rtl/core/mosaic_rob.sv`: the rename and ROB rules above are prose restated in
C++, and this case therefore proves the arbiter against those rules — not that
the elaborated rename and ROB obey them. That is a real boundary of the
evidence, not an oversight, and it is repeated in *Not verified*.

With one rename writeback port only one bank is written per cycle; the per-cycle comparison requires the write-port mask to be exactly the selected destination's home bank, so a destination routed to the wrong bank fails |
| consumer reads the value after the wakeup | `post-wakeup-read` | the wakeup is sampled *before* the edge of the cycle it is presented on; the **very next cycle** `(tag, generation)` is read back out of the elaborated register file and must hold the woken value with no generation mismatch, and the retire stash must hold it too |

The "value is visible when ready" claim was previously argued combinationally
(the write port presents the value in the wakeup cycle). It is now *observed*:
the woken identity is read out of real storage on the first cycle a consumer
could use it.

Three conservation identities are asserted over the whole run:

* `offered == published` — the arbiter holds, never drops;
* `wakeups == writes` — every durable write publishes exactly one wakeup;
* `published == writes + stale + duplicate + refused_destinations +
  no_destination_completions` — nothing else may consume a publication.

the whole run and one first mismatch, so the meaningful delta is 0 → 1 failures;
`checks` is unchanged because the failing check replaces the passing one).

What each control injects, and why its first failure is that rule's own check:

* **`EARLY_WAKE`** — `write_ok = dst_ok`: the PRF write *and* the wakeup are
  driven by "has a destination" instead of "rename accepted it". The first
  refusal is the stale completion, so the per-cycle write-port comparison fails
  on it.
* **`SAMEBANK_DROP`** — the loser of a same-bank pair is cleared from the pending
  set instead of held. The producer was told `wb_ready`, so the runner never
  stops waiting: the conservation identity fires as the bounded drain guard.
  This is the card's "冲突结果丢失而不延迟" as a defect.
* **`STALE_WRITES`** — the "already written" half of rename's answer is dropped
  on the stale side: a completion for an old generation of the tag writes and
  wakes. Same first-refusal point as `EARLY_WAKE`, different `write_ok` (it still
  requires ROB liveness and still refuses duplicates).
* **`DUP_WRITES`** — a second producer for an already-written generation writes
  again, overwriting the first value. Fails in the duplicate phase.
* **`ROB_STALE_WRITES`** — the ROB liveness answer is dropped, so a discarded
  macro's completion reaches a physical register. Fails in the rob-dead phase.
* **`WAKE_NO_WRITE`** — `wu_valid` is independent of `write_ok`: the wakeup is
  published for a completion the register file did not take. Fails on the
  `wu_valid` comparison (the PRF port is untouched, which is exactly the point).
* **`RT_TAG_ONLY`** — the ready table answers from `rt_valid[tag]` alone. Fails
  where the same tag is queried at another generation.
* **`WR_CTR_PUB`** — `o_wr_ctr` counts offered destinations instead of durable
  writes. Fails on the counter comparison one cycle after the stale completion.

None passes identically, so none is a redundancy probe. `EARLY_WAKE` and
`STALE_WRITES` share a first-failure *location* (the stale completion is the
first refusal for both) but are different injections: `EARLY_WAKE` ignores rename
acceptance and ROB liveness, `STALE_WRITES` ignores only acceptance and still
honours liveness and duplicates.

## The card's Fail criterion

> FU done 提前 wakeup，而值在后续争用中失踪.

Stated as a defect: wake a consumer for a completion the register file did not
take, so the value is missing when the consumer reads it under contention.
`MOSAIC_WB_MUTANT_EARLY_WAKE` is exactly that, and it exits 1 at
`stale-result: cycle 21`. The new `post-wakeup-read` phase is the positive form of
the same claim: the woken identity is read out of the register file on the cycle
after the wakeup and holds the woken value.

## Not verified

* **Rename and the ROB are models, not the elaborated modules.** The case does
  not compile `mosaic_rename.sv` or `mosaic_rob.sv`; it proves the arbiter
  against the documented write/liveness rules, not that those modules implement
  them. I-013 and I-016 own that.
* **A *recycled* generation number.** The ready table keeps one
  (written, generation) pair per tag and has no reallocation input, so it
  distinguishes generations by their numeric value. If a tag is written at
  generation G and, after the 7-bit allocation counter wraps, is reallocated to
  generation G again, the table answers "written" for G until the new producer
  writes. The driver does not query that window: by the table's own literal
  contract ("has this (tag, generation) been written") the answer is correct, and
  the hazard is really about the generation width relative to the number of
  allocations a tag can be live through — a cross-module property, not a defect
  this module can fix with its current ports. Recorded in the RTL header.
* **Only p0.** The case asserts four banks and a 7-bit rename generation and
  fails loudly on a geometry change; no other profile was elaborated.
* **One seed.** `seed 1`, as registered.
* **`rob_cmp_bad_uop` is never driven.** No phase offers a completion whose child
  index the ROB does not own, so `o_rob_bad_ctr` stays 0; the conservation
  identity covers the bucket but it has no positive stimulus.
* **`o_store_ctr` is exercised lightly** (3 no-destination completions against 46
  loads); the counter is compared every cycle against the tally, but no phase
  stresses a store-heavy mix.
* **Dispatch's use of the ready table is not modelled.** The query is driven
  combinationally by the driver; that dispatch actually consults it at insert
  time, and what it does with a "not written" answer, is I-023/I-029 territory.
* **The retire consumer of the value stash is not in this case.** The stash is
  read back and checked; that `mosaic_retire` reads it for exactly the right
  macros is I-017.
* **The PRF's own rules** (bank conflicts between read slots, write-through
  bypass) are exercised incidentally but belong to I-015; this case checks only
  that the bank the arbiter names is the bank that takes the write.
* **No timing, area or synthesis claim**, and no assertion about the arbiter
  under `--x-assign` values other than `unique`.
