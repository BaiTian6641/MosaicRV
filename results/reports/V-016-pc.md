## 1. What is compared, and against what

Nothing comes from the DUT. Each program is emitted instruction by instruction by
`tb_core_pc.cpp`'s own encoders (checked against `riscv64-elf-as -march=rv64im` /
`objdump -d` at authoring time), and the architectural stream is computed by the
file's own **RV64IM interpreter**, written from the ISA text: it decodes the same
bytes, keeps its own register file and its own memory, and treats FENCE / FENCE.I
as ordering no-ops — it always reads current code, which is exactly the "after
FENCE.I the new code is observed" rule. It stops only where a program's story
ends (the exit store, or a PC it cannot fetch) and it `Fail`s loudly on any
opcode it does not implement, so it cannot silently agree by doing nothing.

Per retired instruction the case checks, against that reference:

1. **`pc_before`** — the record's own `ev_pc` — equals the reference's PC;
2. **`pc_after`** — the PC the instruction hands control to — equals the *next*
   record's `pc_before`, and that equals the reference's `next_pc` (see §2);
3. the instruction's own **length** (four bytes: every program here is RV64IM)
   and its own **bits**, read from the image;
4. the destination, the write enable and the **value** — which is where the JAL
   and JALR **link** values are checked, since the link is an ordinary register
   write (`link = pc + the instruction's own length`);
5. the **JALR target**: bit 0 cleared and *nothing else* changed
   (`next_pc == raw_target & ~1`), and for a jump-and-link the link is `pc + 4`;
6. **no trap lane** on any record;
7. the **taken branch's target** and the **not-taken branch's fall-through**,
   stated as the PC after each branch;

plus the structural facts the reference cannot state:

8. every fetch request the core makes is an instruction's **own start address**
   (an address inside an instruction is a PC advanced by the wrong amount; an
   address the image cannot serve is allowed, because that is how a runaway or a
   wrong-path fetch ends);
9. the fetch issued in the cycle an answer is accepted is the instruction's own
   length further on — the machine's own statement of the PC advance;
10. `illegal`/`unsupported` stay at zero and no trap is taken while a program runs
    its own story (the one exception is `fetchfault`, where the refusal *is* the
    behaviour under test — see §7).

Nothing is compared after masking a PC, and nothing is compared only when it
agrees: the comparison is over the full 64-bit PC and the full instruction bits.

## 2. `pc_before` and `pc_after`: what the p0 event port actually carries

The V-008 event schema carries both `pc_before` and `pc_after`, but p0's
out-of-order retire port publishes only the former: `mosaic_retire`'s lane
outputs are `ev_pc`, `ev_len`, `ev_insn`, `ev_id`, the payload and the trap
fields, and `results/reports/V-008-events.md` §5 records `ev_pc_after` as one of
the three fields **with no RTL producer yet** (rules F-3/F-4), alongside
`ev_insn` and `ev_trap_epc`. This case therefore checks `pc_after` where the port
does carry it: as the **next record's `pc_before`**, compared against the
reference's `next_pc` for that instruction. That is an ISA-derived statement of
the PC after the instruction, not a re-reading of the DUT, and it is the check
that the link and target statements are folded into: a wrong target, a wrong
fall-through, or a skipped instruction all show up as a `pc_after` disagreement
at the first instruction they affect.

## 3. The boundary this case uses (and what it is worth)

p0 has **no cache and no MMU**: the core asks for four bytes at the instruction's
own PC (`mosaic_core`'s `imem_req.addr = fetch_next_pc`, `size = SZ_WORD`) and the
*harness's memory model* is what assembles them. The boundaries are therefore
this harness's own model, and the report says exactly what they are:

* **the line — eight bytes.** The same model I-041's cross-boundary case uses.
  `line` places a 32-bit instruction at **0x80000FFE**, so its four bytes
  (0x0FFE..0x1001) cross the eight-byte line front at 0x80001000. It retires with
  `ev_len == 4` and its own four bytes, and the case counts it
  (`line_straddles = 2`: the instruction at 0x0FFE and the one at 0x1006).
* **the page front — 4 KiB, at 0x80001000.** `pages` branches from 0x80000008 to
  0x80001004 (upward) and from 0x80001008 back to 0x80000FD0 (downward); the
  `line` run's instruction at 0x0FFE straddles it as well (`page_straddles = 1`).

**A page boundary is not meaningful to p0 in any deeper sense**, and this case
does not pretend otherwise: nothing in the core decodes an address into a page,
there is no page-fault cause, and no TLB. The page front here is an *address*
boundary the program's transfers and one instruction's own bytes cross — which is
all "across a page front" can mean for a cacheless, MMU-less core. The report's
"not covered" list repeats this.

## 4. The unaligned jump target: what p0 actually does

The card asks for "an alignment fault on a jump target that is not 4-byte
aligned (and what p0 does with it — check the existing cases and the core's
contract before asserting a behaviour)". The checked answer is:

* **`mosaic_branch_target` clears bit 0 of a JALR target and nothing else**
  (`aligned = is_jalr ? {sum[XLEN-1:1], 1'b0} : sum`), and its header states that
  bit 1 is deliberately *not* cleared because the misaligned-target report is the
  core's job at the fetch boundary. The `transfers` run produces exactly this
  situation: `ori a1, a1, 1` makes the computed target 0x8000003D, and the JALR
  retires with its link (0x80000034) and hands control to **0x8000003C**.
* **A target that is 2 mod 4 is not a fault in p0.** The core implements the C
  extension (I-041), i.e. IALIGN = 16, under which a 2-mod-4 PC is legal; the
  `line` run jumps to 0x80000FFE and the instruction there retires with its own
  four bytes and the next PC 0x80001002. `o_csr_trap` stays 0 for the whole run.
  The C extension is what makes a 32-bit instruction at 2 mod 4 legal at all
  (I-041's `mixed` run is the other place this is stated).
* **The integrated core produces no instruction-address-misaligned exception at
  all.** `EXC_INSN_MISALIGNED` is defined in `mosaic_pkg`, but the only producer
  of it in the tree is `mosaic_bringup_core` (the bring-up core); `mosaic_core`
  has no instruction-misaligned check on a redirect or a fetch PC. So there is
  nothing for a *jump target* to trigger: bit 0 is architecturally cleared by
  JALR, and bit 1 is architecturally legal. The case asserts the behaviour that
  exists (no fault, the target is reached, the bytes are the ones at that PC) and
  does not assert a trap that the machine cannot produce.

The related **gap** worth naming: p0's CSR config declares IALIGN = 32
(`config/csr/mode_m.json` → `mepc[1:0]` read-only zero, recorded in
`results/reports/I-041-compressed.md` §4), which is not what the C extension
needs. This case cannot expose it, because it takes no trap on a 2-mod-4 PC and
therefore never writes `mepc`. It is listed under "not covered".

## 5. The wrong-path fetch: produced, and leaving nothing

`wrongpath` makes the situation unambiguous: a taken branch at 0x80000004 whose
target is 0x80000104, and a taken JAL at 0x80000108 whose target is 0x80000208,
with **both skipped regions deliberately unmapped** in the harness's image. Every
fetch into either region is therefore answered with an instruction-access fault
(`imem_rsp_fault`), which the fetch unit reports as a refused delivery that the
core carries into the decode buffer as a fully undecodable macro.

The run is guaranteed to fetch there because **the predictor is tied off in this
integration**: `mosaic_core` wires `pred_valid = 1'b0` into `mosaic_fetch`, so
the front end always predicts fall-through and *every* taken branch is a
mispredict whose fall-through is fetched before the redirect. The case states
where it fetched and that it faulted (8 faulting fetches across the two regions,
asserted per region), and then asserts the architectural silence:

* **no instruction retires at any address a transfer skipped** (the leak check);
* **the machine never stops** on the wrong-path fault;
* **the wrong-path fault never reaches dispatch as a refused macro**
  (`illegal == 0 && unsupported == 0`);
* **no trap** is taken (`o_csr_trap == 0`), and the program reaches its exit
  protocol.

This is the area the dispatch fix touched (`mosaic_dispatch` holds an
undecodable macro while a transfer is in flight, `l0_refused = l0_unsupported &&
!branch_in_flight`, and the redirect purges the buffer). **No hole was found:**
the shipping build squashes all eight faults and runs to completion. Control (c)
below shows the check has teeth: with the purge removed, the leak is caught.

## 6. FENCE.I, from the fetch side

`fencei` is the card's "the new bytes are the ones executed". The word
immediately after FENCE.I is fetched early (the front end runs ahead of the ROB),
a `sw` patches it once a slow `div` has let the store drain, they FENCE.I
executes, and the record at FIXPC must carry the **patched** word
(`0x02200513`, `addi t2, x0, 0x22`) and the patched effect. A FENCE.I that does
not invalidate the delivered view executes the stale `0x01100513` instead — which
is what control (b) injects and the case catches. The reference predicts the
patched instruction because it always reads current memory, so the *expectation*
is the ISA's, not the machine's.

The two fences themselves are not this case's subject — `CASE=fence.code_and_data_order`
(I-037) owns the ordering contract — but that case is re-run below because this
one shares its machinery.

## 7. The fetch-fault path: a stop, not a trap

`fetchfault` answers the card's question directly. A JALR on the *correct* path
computes 0x80000100, which the image cannot serve; the fetch faults; the refused
delivery reaches dispatch as an undecodable macro and **the machine stops at it**.
The case asserts:

* `o_stopped` is high, and **`o_csr_trap` is zero** — p0 does not take a
  synchronous trap for an instruction-access fault;
* nothing retires at 0x80000100;
* the fault is reported at the faulting instruction's **own start address**
  (`o_dbg_fetch_o`'s delivery PC with the deliverable bit low).

So in p0 the fetch-fault path is a **stop**, not a trap. That matches
`results/reports/I-041-compressed.md` §4 ("In p0 a fetch access fault is a stop")
and is a known gap relative to the ISA, repeated under "not covered".

## 12. Not covered (honest list)

* **A page boundary as anything other than an address boundary.** p0 has no MMU
  and no cache, so there is no page-crossing behaviour to exercise; the `pages`
  and `line` runs cross a 4 KiB front in the addresses they use, which is all a
  cacheless core can see (§3).
* **An instruction-address-misaligned trap.** The integrated core produces none
  (only `mosaic_bringup_core` does), and the two situations that could reach one
  are architecturally impossible or legal: JALR clears bit 0, and a 2-mod-4 PC is
  legal under the C extension. Asserting a trap here would assert a behaviour p0
  does not have.
* **A fetch *trap*.** A correct-path instruction-access fault is a **stop**, not a
  trap (§7), so the case asserts the stop. When a trap path for instruction-access
  faults exists, this run should become a trap record with cause 1 at the same PC.
* **`mepc` on a 2-mod-4 PC.** Not exercised: no trap is taken on one, so `mepc` is
  never written. p0's CSR config declares IALIGN = 32 and zeroes `mepc[1:0]`, which
  is not what the C extension needs — the same gap I-041 recorded, owned by the
  IALIGN move, not by this case.
* **A wrong-path *misaligned* fetch.** Cannot be produced for the reason in the
  previous bullet; the wrong-path exception this case produces is an
  instruction-access fault.
* **A wrong-path fetch behind a *not-taken* branch.** The predictor is tied off,
  so a not-taken branch's fall-through is the correct path; the wrong-path fetch
  here is behind a taken branch whose fall-through is fetched first (a mispredict),
  which is the only wrong-path fetch such a machine makes.
* **A cache-line refill.** There is no L1I yet (I-042), so "a straddling
  instruction assembled across a refill" is not exercised; the memory model
  assembles the four bytes directly.
* **Interrupts.** Tied off (`irq_* = 0`), so no wrong-path fetch competes with an
  interrupt taken at the head; that interaction belongs to `irq.replay_timeline`.
* **The whole of RV64IM in the reference.** The interpreter implements only the
  subset these six programs use (LUI, AUIPC, ADDI/ORI/ANDI, SLLI, ADD/SUB, DIV,
  SW/SD, BEQ/BNE/BLT/BGE, JAL, JALR, FENCE, FENCE.I) and `Fail`s loudly on
  anything else, so it cannot silently skip an instruction the DUT executed.
* **A cross-check against a second ISS.** The expectation is this file's own
  interpreter, not NEMU or Spike; a differential run against an independent ISS is
  a different package's job.
