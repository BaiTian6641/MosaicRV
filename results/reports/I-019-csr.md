## Single source of truth: what the generator emits, and why

`config/csr/mode_m.json` is the implementation table. `render_sv_csr_package()`
decodes it to one `localparam` block per CSR:

```
  localparam logic [11:0] MOSAIC_CSR_ADDR_MSTATUS     = 12'h300;
  localparam logic [63:0] MOSAIC_CSR_RESET_MSTATUS    = 64'h0000000000001800;
  localparam logic [63:0] MOSAIC_CSR_WMASK_MSTATUS    = 64'h00000000000066aa;
  localparam logic        MOSAIC_CSR_WRITE_LEGAL_MSTATUS = 1'b1;
```

The module names those constants (`mosaic_csr_pkg::…`, fully qualified — no
`import`, per the Yosys rule) and contains **no CSR number, no reset value and no
mask** of its own. The testbench's model reads the same table from the generated C
header. So there is exactly one copy of every configured number in the tree, and
`make check` / `check_profile.py --all` / `check_contracts.py --all` still
validate that copy.

**What is shared is the data; what is independent is the behaviour.** The shadow
model re-derives the trap/MRET transitions, the WARL canonicalisation, the
boundary priority and the counter arithmetic from the contract prose — it shares
no code with the RTL. To make sure the shared *data* cannot hide a decode bug,
phase 1 ("table") cross-checks all 21 generated rows against values transcribed by
hand from `config/csr/mode_m.json` and the clauses it cites (addresses, reset
values, the seven write-less CSRs, `mstatus` = `0x66aa`, `mepc` = `…fffc`,
`mie`/`mip` = `0x88`, `mtvec` = all ones, `medeleg`/`mideleg` = 0). A wrong decode
therefore fails loudly at the start of the run instead of making both models agree
on a wrong number.

### Two integration fixes to the generator (requested by the integration lead)

Both were reported by Main while this package was in flight and are in
`tools/gen_manifest.py`:

1. `mosaic_id_pkg.svh` had no include guard. Four or more files include it in one
   compilation unit, so `slang-tidy --single-unit` reported a duplicate package
   definition for the whole repo. Now guarded with `MOSAIC_ID_PKG_SV_`.
2. The generated packages are compiled into every including file, so an unused
   constant or an unused function argument in the generated text is a warning
   *against the consumer*, and a warning is a failure here. `mosaic_id_pkg` and
   `mosaic_csr_pkg` now carry `/* verilator lint_off UNUSEDPARAM */` … `lint_on`,
   and `mosaic_id_pkg` an `UNUSEDSIGNAL` pair around its identity functions;
   `mosaic_cfg_pkg` got the `UNUSEDPARAM` pair too. No emitted number changed.

Main also fixed, in the same file, a comment I had emitted whose first word was
`Verilator` — that makes it a Verilator metacomment, and every file including the
header died with `%Error-BADVLTPRAGMA`. I checked afterwards that no generated
file and no `add("// …")` line in the generator has an identifier as its first
comment word.

## Design: the decisions the card asked to be recorded

**Field positions vs. writability.** The module names `mstatus.MIE` = bit 3,
`mstatus.MPIE` = bit 7, `mstatus.MPP` = bits 12:11 (the RV64 layout the clause
cites: bit-number rows L448–L495, field-name rows L462–L474). Which of those bits
software may change still comes from the generated mask, not from this file.

**WARL canonicalisation, per register, with the clause.**

* `medeleg`/`mideleg` (0x302/0x303). The table declares the whole MXLEN field WARL,
  but p0 implements no S or U mode, so no trap can be delegated anywhere and the
  only legal value of every bit is 0 ("p0 is M-only … every bit is WARL whose only
  legal value is 0"; "With no S or U mode there is no delegation target"). These
  are *not* read-only registers, so a write is **accepted and does not trap**; the
  bits canonicalise to 0 and a read returns 0. The generator applies the rule from
  the profile's own `privilege_modes` list and emits a write mask of 0, so a
  profile that adds S or U gets the writable register back with no edit anywhere.
* `mtvec` (0x305). Table mtvec MODE: 0 Direct, 1 Vectored, **≥ 2 Reserved**. A
  reserved encoding has no defined behaviour and must not be read back, so it is
  canonicalised to **Direct (0)** — the value the register resets to. BASE occupies
  bits 63:2, and the mode bits are written by the same rule, so BASE is 4-byte
  aligned by construction (L1181–L1183).
* `mepc` (0x341). IALIGN = 32 in p0, so `mepc[1:0]` are read-only zero
  (L1935–L1937). The generated mask excludes them and the trap path masks the trap
  PC with the same mask, so a misaligned trap PC cannot be installed either.
* `misa` (0x301) and `mcounteren` (0x306) are WARL registers with **no writable
  bits**: access is `rwr`, so a write is *legal and changes nothing* — raising
  illegal-instruction for a write to `misa` would contradict "The misa CSR is a
  WARL read-write register" (L22). The seven genuinely read-only CSRs
  (`mvendorid`, `marchid`, `mimpid`, `mhartid`, `cycle`, `time`, `instret`, all
  access `ro`) refuse writes with `csr_wr_illegal_o` and change nothing. The
  `read-only` phase checks both classes separately, precisely so this distinction
  is pinned down.

**mstatus transitions.** Trap entry: `MPIE ← MIE`, `MIE ← 0`, `MPP ← current
privilege`; MRET: `MIE ← MPIE`, `MPIE ← 1`, `MPP ← least-privileged supported
mode` (Privileged Spec v1.12 §2.1.6.1). In p0 the last two are both M = 3, and
`MPP` is read-only 3 in this table (bits 12:11 absent from the write mask, reset
`0x1800`). The hardware writes M into MPP on both paths anyway, so the rule is
visible rather than implied by a constant — which is also what makes the
`MPP_CLEARED` mutant observable.

**Boundary priority.** Strictly `trap_valid_i` > `mret_valid_i` > `csr_we_i`; a
lower-priority request in the same cycle is dropped rather than merged. A trap
outranking a retiring CSR write is what makes the trap precise: the instruction
that trapped contributes no retirable CSR write (checked directly — mscratch is
unchanged and `o_wr_ctr` does not move). A trap and an MRET are mutually
exclusive, and the RTL asserts it:

```systemverilog
  always_comb begin
    assert (!(trap_valid_i & mret_valid_i));
  end
```

**That assertion is live in the Verilator build, not decoration.** The first
version of the testbench drove both events in one cycle to check the resolution;
the run aborted with `%Error: mosaic_csr.sv:303: Assertion failed in
TOP.mosaic_csr_tb.u_csr`, which is how I learned Verilator 5 checks immediate
assertions by default. The testbench now never presents the combination, and a
passing run *is* the proof of the exclusion.

**mip.** Owned by `mosaic_interrupt` (I-020). This module stores no mip state: a
read returns `mip_i` masked to the two implemented bits (p0 has a CLINT driving
MSIP and MTIP and no PLIC, so MEIP reads zero), and a write is forwarded on
`mip_we_o`/`mip_op_o`/`mip_wdata_o`. Because mip is not stored here, the card's
"write all-ones to every CSR and require the mask-implied value back" cannot apply
to mip; the `warl` phase checks the forward and the masked read instead, and says
so.

**Counters.** `mcycle`/`minstret` are free-running and MRW. A write and an
increment in one cycle have one defined outcome:

```
next = (write_accepted ? written_value : current) + tick
```

so writing `V` in a cycle where the counter ticks reads back `V + 1`. Rationale:
the counter counts clock cycles by definition, so an instruction must not be able
to delete a cycle from it; the alternative (a write suppresses the tick) would
make the counter depend on exactly when the write landed relative to the clock,
which software cannot control. The `counters` phase drives both in one cycle and
requires `V + 1`. `cycle`/`instret` shadow the counters and `time` shadows
`mtime_i`; all three refuse writes.

**Reads.** The read port is combinational over the registers and never depends on
`csr_wdata_i`, so a write retiring in cycle N is first readable in N+1. The
`READ_AFTER_WRITE` mutant shows the difference is detected.

## What the test does

`sim/unit/tb_csr.cpp` holds a model of all 21 CSRs and 9 phases, each of which
resets both models first and can fail on its own:

1. **table** — the generated table equals the hand-derived one (see above).
2. **reset-state** — all 21 addresses read their declared reset value.
3. **read-only** — the seven `ro` CSRs refuse writes (`csr_wr_illegal_o` rises,
   the value is unchanged, reads still work) and `misa`/`mcounteren` accept a legal
   write that changes nothing.
4. **warl-allones** — for every writable CSR, all-ones with RW and RS, all-ones
   with RC (leaving the reset-only bits), and a mixed `0x0f0f…` pattern, each
   required to equal the mask-implied value; then mtvec's reserved MODE 2/3
   canonicalisation and MODE 0/1 preservation; then mip forwarding.
5. **illegal-addr** — 26 legitimate-looking unimplemented addresses (0x000, 0x307,
   0xB01 `mcycleh`, 0xC03, 0xF15, 0xFFF, …) read 0 and raise `csr_illegal_o`; a
   write raises `csr_wr_illegal_o`; a whole-register-file snapshot is identical
   afterwards.
6. **trap-mret** — entry transitions, MRET restore, a second MRET, nesting, the
   MPIE-already-zero case, and trap priority over a retiring CSR write.
7. **causes** — all 9 exception codes in `mosaic_pkg`'s list and 7 interrupt codes
   (including a custom code ≥ 16 and 63), in Direct and Vectored mode: recorded
   mepc/mcause/mtval/mstatus and the entered target equal to the model; a
   synchronous exception enters at the base even in vectored mode; a vector offset
   never carries into the base.
8. **counters** — increments, write+tick in one cycle, exact writes without a
   tick, read-only shadows, `time` shadowing `mtime_i`, and the exact observability
   counter values.
9. **random** — 6 000 cycles of reads, all three write ops, illegal addresses,
   ticks, traps (with deliberately misaligned trap PCs) and MRETs, with every
   observable compared against the model every cycle, plus an end-of-campaign
   cross-check that the model's own event counts equal the DUT's counters.

Two-snapshot discipline throughout: combinational outputs (`csr_rdata_o`,
`trap_target_o`, `mip_we_o`, …) are compared before the edge against the model
computed from the same pre-edge state; the registered observables are compared
after it. `RESULT : FAIL` on any disagreement and the first mismatch names the
cycle, the signal and the stimulus.

Standing invariants checked on the DUT's own outputs every cycle: `mstatus.MPP` is
always 3, `mtvec.MODE` is never reserved, `mepc[1:0]` is always 0, `mie` has no
bit outside its implemented bits, and `mip` reads no bit it does not implement.

## Mutants

Recipe (as documented in the project brief):

```python
import sys; sys.path.insert(0, 'tools'); import run_unit
run_unit.VERILATOR_FLAGS.append('-DMOSAIC_CSR_MUTANT_<NAME>')
run_unit.build_case('p0', CASE, run_unit.load_registry()['cases'][CASE])
# then: build/p0/unit/<CASE>/<CASE> --case <CASE> --out /tmp/mut --seed 1 --max-cycles 200000
```

Base: `checks=10, failures=0, exit 0`. Every mutant below: `failures=1, exit 1`,
with a distinct first mismatch naming the injected defect. Each `ifdef` body
exists in the shipping file (line numbers from `rtl/core/mosaic_csr.sv`), which is
what the three earlier "empty ifdef" incidents in this project demand:

| Mutant | Line(s) | What it breaks | Exit | First mismatch (delta: 0 → 1 failure) |
|---|---|---|---|---|
| `MIE_KEPT` | 457 | trap entry sets MPIE but leaves MIE set | 1 | `trap-mret: cycle 454 o_mstatus_o: expected 0x…1880, saw 0x…1888` |
| `MRET_NO_RESTORE` | 466 | MRET sets MPIE but does not restore MIE | 1 | `trap-mret: cycle 459 o_mstatus_o: expected 0x…1888, saw 0x…1880` |
| `MPP_CLEARED` | 473 | trap entry clears MPP instead of writing M | 1 | `trap-mret: cycle 454 o_mstatus_o: expected 0x…1880, saw 0x…0080` |
| `READ_AFTER_WRITE` | 338 | write operand appears on the read port combinationally | 1 | `read-only: cycle 31 csr_rdata_o: expected 0x0, saw 0xffffffffffffffff` |
| `RO_WRITE_ACCEPTED` | 275 | a write to a read-only CSR is reported legal | 1 | `read-only: cycle 31 csr_wr_illegal_o: expected 1, saw 0` |
| `CYCLE_WRITABLE` | 281, 444 | cycle/instret writes legal *and* land in the counters | 1 | `read-only: cycle 43 csr_wr_illegal_o: expected 1, saw 0` |
| `CYCLE_WRITE_LANDS` | 480 | the write is still refused at the port but lands in mcycle | 1 | `read-only: cycle 43 o_mcycle_o: expected 0x0, saw 0xffffffffffffffff` |

**Substitution, stated plainly.** The card's list asks for "MPP not updated on
entry". In p0 that mutant is **unobservable**: bits 12:11 of `mstatus` are in
`unmodifiable_bits` and the reset value already has MPP = 3, so "not updating" and
"updating to the current privilege (M = 3)" are the same value on every cycle. I
therefore mutated the transition in the only direction that can be seen —
`MPP_CLEARED`, entry forcing MPP to 0 — and the invariant check and the model both
catch it. A mutant that could not be observed would be worse than no mutant,
because it would look like evidence.

`CYCLE_WRITABLE` was split into two mutants on purpose: as written it corrupts both
the legality report and the counter state, and the report is what fires first. The
narrower `CYCLE_WRITE_LANDS` leaves the report honest and corrupts only the state,
so the state comparison is shown to catch it too.

## Not verified

* **The retire unit's half of the contract.** "The destination register of the
  trapping instruction must not be written" and "a trap does not increment
  minstret" are I-017's event stream: this case drives `cnt_instret_i` directly and
  never instantiates `mosaic_retire`. What *is* checked here is the CSR side of it —
  a trap suppresses a same-cycle CSR write and `o_wr_ctr` does not count it.
* **mip ownership.** `mip_we_o`/`mip_op_o`/`mip_wdata_o` are checked as forwarded
  values; nothing in this case applies them to a pending register. That is I-020.
* **Privilege violations.** p0 is M-only, so no CSR access can be illegal for
  privilege reasons and the frozen interface has no port for one. "Any other
  address is illegal" is checked; "any other *mode*" cannot exist here.
* **Interrupts.** No interrupt is ever sampled to generate `trap_valid_i` with
  `mcause[63]` set by hardware; the input is driven directly, including the
  vectored-interrupt target arithmetic.
* **`mtval` policy.** Which exceptions set `mtval` informatively is a platform
  policy (recorded as an open ambiguity in `results/reports/I-001-csr-m.md`); this
  module stores the value it is given verbatim.
* **Formal proof, coverage closure, and the full-core synthesis gate.** The
  scoped Yosys run above is a smoke test of this module alone. `make synth-generic`
  walks `rtl/` and therefore reads this file, but I did not run the whole-design
  gate (other lanes are mid-edit).
* **mcause's WLRL policy on unsupported codes.** The module stores whatever
  `trap_cause_i` carries; the "only supported codes are guaranteed" rule (L1990)
  is enforced, if at all, by the exception source, not here.

## What I would add to `results/PROGRESS.md` (not edited — owned elsewhere)

Two conventions from this package that a future reader of the progress log needs:

1. A generated header is compiled into every including file, so it must carry its
   own include guard *and* its own Verilator lint pragmas, and a comment line in it
   must never begin with the word `Verilator` (that is a metacomment, and
   `BADVLTPRAGMA` blocks every consumer). `mosaic_cfg_pkg.svh`, `mosaic_id_pkg.svh`
   and `mosaic_csr_pkg.svh` all satisfy this now.
2. Verilator 5 checks immediate assertions by default, so an assertion in the RTL
   is a *live* failure in every unit build, not documentation. A testbench must
   not present an input combination the RTL asserts against.

## Findings for other lanes (reported, not edited)


1. **`rtl/core/mosaic_retire.sv` duplicates CSR state.** It holds its own
   `mcycle`/`minstret`/`mscratch` registers and its own copies of addresses
   `0xB00`, `0xB02`, `0x340` (its comment says the CSR unit "will implement these
   three plus the rest"). That is a second copy of a configured number *and* a
   second copy of the architectural state. The cutover — retire forwarding its CSR
   events to `mosaic_csr` instead of applying them locally — is the I-017/I-019
   boundary and belongs to the retire owner; it is not in this card's file list, so
   I did not touch it.
2. **`rtl/core/filelist.f` does not list `mosaic_csr.sv`** (nor `mosaic_retire.sv`,
   `mosaic_recovery.sv`, `mosaic_fetch.sv`), so the *generated* `filelist.f` and any
   consumer of it do not see this module. `tools/synth_check.py` walks `rtl/`
   directly, so the synthesis smoke test does cover it — but whoever owns the
   filelists should add the line. I left the file alone because it is a shared
   integration point with several lanes in flight.
3. **`make lint-cpp` is currently red** for a reason unrelated to this package:
   `sim/unit/tb_muldiv.cpp` needs `Vmosaic_muldiv_tb.h`, which only exists once
   that case has been built. Building any unbuilt case before linting fixes it.
4. **The RTL assertion is active in the Verilator build** (Verilator 5 checks
   immediate assertions by default). Any caller that presents `trap_valid_i` and
   `mret_valid_i` together will abort the simulation rather than take a defined
   branch. That is deliberate, but it is worth knowing before someone writes a
   random stimulus generator against this module.
