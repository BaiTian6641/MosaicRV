## The walk as a rule

The walker is `rtl/core/mosaic_ptw.sv`. It implements the privileged
specification's *Virtual Address Translation Process* step for step, and the
step order **is** the fault priority:

| # | rule | this implementation |
|---|---|---|
| 1 | canonicality: bits 63:39 must all equal bit 38 (Sv39) | tested in `ST_IDLE`, **before any PTE is read**; failure is a page fault of the access class |
| 2 | read the PTE at `pt + 8*vpn[i]` | one 8-byte read on the PTE port per level |
| 2 | a PMA/PMP refusal of that implicit read | **access fault** of the access class (1/5/7), not a page fault |
| 3 | V=0, or W=1&R=0 (reserved), or a bit reserved for future standard use (63:54) set | page fault of the access class |
| 4 | R=1 or X=1 → leaf; otherwise descend; a non-leaf at level 0 | page fault |
| 5 | permission check against R/W/X, U, SUM, MXR | page fault |
| 6 | `i>0` and the low `i*9` bits of the leaf PPN nonzero | misaligned superpage → page fault |
| 7 | A=0, or a store with D=0 | hardware update (compare-and-set, below) |
| 8 | compose `pa`: offset untranslated, superpage low VPN bits from `va`, rest from the leaf | — |

Level order is 2 → 1 → 0 with 9-bit VPNs and 8-byte PTEs. Superpage alignment
is `pte.ppn[17:0]==0` at level 2 and `pte.ppn[8:0]==0` at level 1. Address
composition: `pa[55:12] = {pte.ppn[43:18], va[29:12]}` (level 2),
`{pte.ppn[43:9], va[20:12]}` (level 1), `pte.ppn` (level 0); `pa[11:0]=va[11:0]`.

Permissions, from the specification's text: a **store** (including AMO/SC) needs
W; a **fetch** needs X; a **load** needs R, or X when `mstatus.MXR=1`. MXR is
the specification's one-directional rule — it makes *executable pages readable*;
it does **not** make a readable page executable, so a fetch from an R-only page
faults whatever MXR says. The U bit: U-mode needs U=1; S-mode on a U page needs
`mstatus.SUM=1` for a load/store and **can never fetch** from it, SUM or not.
Privilege M is a passthrough (the caller should not ask, but the correct answer
if it does is "the virtual address is the physical address").

Fault priority when several things are wrong at once is the step order: a
non-canonical address beats everything (no physical access); an implicit access
fault beats an invalid PTE; an invalid/reserved PTE beats a permission fault;
a permission fault beats a misaligned superpage; A/D last. All of a leaf's
permission failures produce the *same* cause (the access class), so priority
within step 5 is not observable.

## The A/D policy (explicit)

The **hardware-update** scheme is implemented, not Svade:

* a leaf with **A=0** is updated by setting A only;
* a leaf **written by a store/AMO** with **D=0** is updated by setting A and D;
* the update is a compare-and-set: the walker re-reads the PTE, and only if the
  value is unchanged does it write it back (always 8 bytes, full strobe). A
  mismatch re-evaluates the fresh value instead of writing a stale update;
* a PTE write the memory refuses is an **access fault** of the access class
  (step 7's own rule);
* A is set by a load, store or fetch; D is set **only** by a store.

A PTE with A=0 (or D=0 for a store) therefore **does not fault** in the shipping
build: the walk maintains the bits and completes. `Svade` is not implemented, and
the case's A/D cells check the bits in the page table before and after the walk.

### The integration (run through the core)

A small program (M-mode, `mprv`-free) writes `satp` = Sv39(root), programs one
unlocked TOR PMP entry covering RAM, and `mret`s into **S-mode**. The S-mode stub
performs a translated load and a translated store, then a non-canonical load and
a V=0 load; the M-mode handler records `mcause`/`mtval` and returns. The driver
watches the core's data port and requires:

* the Bare-phase load/store are untranslated (`va == pa`), observed on the port;
* the S-mode load's **physical** read and the store's **physical** write appear on
  the data port, and the value round-trips through the mapped page;
* the three PTE reads of each walk appear on the port in level order;
* the non-canonical load takes cause 13 with `tval = va`, and the V=0 load takes
  cause 13 with `tval = va`;
* **no port transaction is outside RAM** (the card's first failure mode: a
  non-canonical address reaching physical memory would show as a PTE read or a
  data access at an out-of-RAM address).

The store's translation is resolved at the **commit boundary**, before the store
retires, so a page fault on a store is a precise trap (cause 15, `tval = va`)
rather than a post-retirement count. The translated physical address is recorded
in a FIFO and the drain writes to it, so a `satp` write that retires between the
store's retirement and its drain cannot change where the store lands.

## Not covered (honest list)

* **TLB and `SFENCE.VMA` are I-046's.** There is no address-translation cache, so
  **every access re-walks** the page table. The case therefore cannot observe a
  stale translation, and `SFENCE.VMA` is not implemented.
* **Instruction fetch is not translated.** The integration is the data path only
  (`mosaic_lsu_endpoint.sv`/`mosaic_core.sv`); `mosaic_fetch.sv` still fetches
  physical addresses. Fetch-*class* access kinds are covered at the walker's own
  interface (cause 12, the X bit, MXR), and the S-mode stub is identity-mapped so
  its fetch is the same address either way — but a real S-mode OS would need the
  fetch-side integration (I-046/I-048).
* **The caches are not in the path.** I-042's L1s are module-level and not wired
  into the core, so no PTE or data access goes through a cache here.
* **Implicit (PTE) accesses are not checked against PMP.** The walker's PTE port
  is merged directly onto `dmem`; the PMP unit is queried only for explicit data
  accesses. The spec requires PMP to apply to implicit accesses; here an implicit
  access that the *PMA* refuses faults (covered by `pte-access-fault-*`), but a
  PMP refusal of a PTE read would not. This is the one deliberate gap the case
  does not close, and it is stated rather than hidden.
* **A store page fault is precise, but a store's translation is resolved at
  commit**, not at issue, so the walk happens once per store at the ROB head. An
  interrupt taken at the head store discards the store (the redirect flushes it)
  and its translation result with it; the store re-executes afterwards.
* **A/D compare-and-set is not truly atomic.** With one hart and one walker in
  flight there is no concurrent PTE writer, so the re-read/compare/write is
  sufficient; a multi-hart or DMA-writer system would need the atomic RMW the
  spec requires.
* **`satp` ASID is not implemented** (`unmodifiable_bits 59:44` in
  `config/csr/mode_su.json`), so writes zero it and no ASID is carried; ASID
  recycling is I-046's.

## `satp`-write visibility without `SFENCE.VMA`

The brief's question, answered: a translation is performed **once, at the
access's own point in program order**, using the committed CSR state at that
moment, and the resulting physical address is what the access uses. A later
`satp` write therefore cannot retroactively change an access that already
executed. For stores this is made literal by the translated-address FIFO (the
store's physical address is recorded at commit and used at drain, even if `satp`
changed in between). For loads the walk is cancelled by the redirect that flushes
a squashed load, so no stale walk result can be attributed to a re-fetched
instruction. The CSR change itself is the profile's WARL rule: `satp.MODE` is
canonicalised to {Bare, Sv39} and an unsupported MODE leaves the register
unmodified (`mosaic_csr.sv`), so the MODE the walker sees is always one it can
execute. `SFENCE.VMA`'s own ordering obligations are I-046's.
