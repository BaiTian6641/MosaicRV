Internally:

Architecturally:

This retains:

Your earlier uOP design already moved in exactly this direction by separating architectural-instruction identity from internal execution uOPs.

11. There are several valuable compound forms

This is where I think the architecture can become substantially more efficient.

Load + ALU

ld  x5, 0(x10)
add x6, x5, x7

normally:

LOAD
 ↓
PRF write
 ↓
wakeup
 ↓
PRF/bypass
 ↓
ADD

could become:

Memory → Tile L0 → ALU

with the intermediate value never permanently written if unnecessary.


---

ALU + store

add x5, x6, x7
sd  x5, 0(x10)

could become:

ALU → Store Queue

rather than:

ALU → PRF → RF read → store data

BOOM already demonstrates the importance of flexibly handling store address and store data: its store can occupy one issue-window entry while allowing address or data portions to progress independently as operands become ready. 

You can generalize this much further.


---

Address generation + load

addi x5,x10,64
ld   x6,0(x5)

becomes:

LD x6,64(x10)

internally.

No intermediate register traffic.


---

Load + modify + store

Your example:

ld   x5,0(x10)
addi x5,x5,1
sd   x5,0(x10)

can become:

L0/L1 load
    ↓
ALU
    ↓
StoreQueue

without:

PRF write
PRF read
global result route

That is exactly the kind of data-movement reduction that suits MEF.

12. But do not accidentally turn ordinary RISC-V code into an atomic instruction

This point matters greatly.

The sequence:

ld
add
sd

is normally not an atomic RMW.

Therefore even if internally represented as:

LOAD_MODIFY_STORE

the store portion cannot simply update memory immediately.

You need:

load
 ↓
compute result
 ↓
Store Queue entry
 ↓
wait for architectural retirement/order permission
 ↓
memory update

So the compound packet means:

> fused execution



not:

> new atomic semantics.



For actual atomicity, use RISC-V AMOs/LR-SC semantics.

And MMIO / strongly ordered memory should generally be excluded entirely from this aggressive path.

13. Memory dependence prediction becomes crucial

Once you become more aggressive, you need to answer:

Can this load safely pass older unresolved stores?

This is where a memory-dependence predictor becomes part of MPP.

The classic Store Sets approach predicts the older store(s) a load is likely to depend on, allowing independent loads to issue aggressively while delaying likely aliases. 

Interestingly, recent 2026 work suggests this doesn't necessarily require a giant predictor: Mini-MDP reports a 48-entry design that gets within 0.06% IPC of a much more complex predictor on its SPEC CPU2017 evaluation while using a small fraction of the comparator design's area and power. 

That fits MEF nicely.

MPP can have:

Memory Intent Cache
+
Address Predictor
+
Small Dependence Predictor

rather than creating another huge scheduler.

14. I would actually create two levels of aggressiveness

This gives you a clean research path.

Level 1 — Preview-only

Prediction can:

translate
prefetch
allocate MSHR
fill L1
fill Tile-L0
choose probable tile

but the actual load must compute its real address and validate ordering before consuming the value.

Wrong prediction:

extra cache traffic only

This is relatively safe.


---

Level 2 — Early consume

High-confidence prediction:

predicted address
       ↓
Tile-L0 already contains value
       ↓
dependent ALU executes

before actual AGU validation has completed.

Now all resulting operations carry something like:

MemSpecEpoch = 17

When real address/order validation arrives:

correct
   ↓
confirm epoch

or:

wrong
   ↓
replay/squash dependent slice

That is considerably more aggressive.

Essentially:

> address prediction becomes value-availability speculation.



I would absolutely not start there, but it is a very interesting second-generation feature.

15. Stores should be asymmetric

I would let the preview pipeline be extremely aggressive about loads and conservative about stores.

Predicted store:

store likely to address X

can safely be used to prepare:

TLB translation
cache-line ownership request
L1 write permission
Store Queue allocation hint
tile placement

but never write predicted data to the architectural cache/memory hierarchy before the ordinary store has been validated and committed.

So:

Predicted LOAD:
may fetch data

Predicted STORE:
may prepare destination
must not update destination

This asymmetry greatly simplifies correctness.

16. "Store prefetch" could nevertheless be extremely powerful

Imagine the system predicts:

sd x5, 0(x10)

will soon write line A.

Instead of waiting until store commit:

IMC:
request line ownership early

In a coherent multiprocessor this means conceptually:

Shared/Read state
   ↓
prefetch-for-write / ownership request
   ↓
exclusive/writeable line ready

Then when the real store reaches commit:

no coherence acquisition latency

That's potentially valuable for producer-heavy code.

Again, you haven't made the store visible early.

You've just prepared everything needed for it.

17. Prediction should also decide L1 vs Tile-L0

Your IMC can use a locality classification:

Predicted behavior	Placement

one-time streaming	L1 or stream buffer, not Tile-L0
repeated same-tile use	Tile-L0
cross-tile shared	shared L1
RVV contiguous stream	coalescer + stream buffer
gather with clustered lines	shared L1 + selective Tile-L0
random	minimize pollution
load→ALU fused chain	destination tile L0
load→store same line	tile near store execution


Now your "tightly coupled cache" becomes active placement memory.

18. I would add line versioning to the Tile-L0

Because you're speculatively placing data near tiles, validation has to be cheap.

Something like:

LineTag
SectorValid
Version
Speculative
SourceL1Bank

line version / invalidation epoch

version++

The previewed load can validate:

If yes:

data still valid

If no:

This could make speculative near-tile copies considerably cheaper than full per-tile coherence.

19. The prediction path should receive branch confidence too

Otherwise you'll prefetch huge amounts of wrong-path data.

MPP request priority should look something like:

confidence =
    address confidence
  × branch-path confidence
  × memory-dependence confidence
  × locality confidence

Then:

very high confidence:
    → Tile-L0 fill

medium:
    → L1 prefetch

low:
    → L2-only prefetch

very low:
    → nothing

That's a particularly elegant mechanism.

The more speculative something is, the farther away from the scarce low-latency structures it stays.

20. Think of the hierarchy as confidence levels

This is perhaps the cleanest formulation of your idea:

Prediction confidence
                          increases
                              ↑

                  Tile tightly coupled L0
                    very high confidence
                              ↑
                            L1D
                       high confidence

So instead of asking:

> "where is this memory address?"

That's a very MEF-like way of thinking.

21. A miss prediction does not have to be wasted

Suppose MPP predicted:

Load A → Tile 2

but the uOP eventually goes to Tile 3.

Don't copy it immediately.

Tile 3 can request:

Tile2 L0 → Tile3

or simply access shared L1.

The placement predictor is therefore just an optimization.

Wrong tile:

+1 hop

not:

pipeline squash

Only a wrong address used for early dependent execution should require recovery.

This is another reason to initially implement preview-only mode.

24. You could even fuse non-adjacent instructions

27. Performance potential

I would expect the mechanisms to contribute approximately this much relative to the MEF architecture without the new preview pipeline:

Feature	General scalar	Memory-sensitive

early address/line prediction	+1–5%	+5–15%
early L1 prefetch	+1–4%	+5–20%
Tile-L0 placement	+1–5%	+3–12%
store destination preparation	0–3%	+2–8%
load→ALU fusion	+2–5%	+2–8%
ALU→store fusion	+1–4%	+2–7%
RMW/dataflow fusion	+1–5%	+3–10%
early-consume speculation	+0–5%	+3–12%


These cannot be added together.

They eliminate many of the same stall cycles.

My combined mature target would be approximately:

\[
\boxed{+5\%-12\%}
\]

additional general scalar performance over the prior MEF design, and perhaps:

\[
\boxed{+10\%-30\%}
\]

on memory-sensitive workloads where prediction works well.

On completely unpredictable pointer chasing:

address predictor accuracy ↓

the improvement may approach zero, at which point runahead/helper execution becomes more useful.

28. This materially improves the chance of beating Kunminghu V2R2

Kunminghu already has an aggressive memory system: its documented core can issue up to three scalar loads, two scalar stores and two vector-memory microinstructions per cycle, with a nonblocking D-cache and hardware prefetching. 

Its LoadUnit also already feeds prefetchers and accepts high/low-confidence hardware prefetch traffic. 

So your advantage cannot simply be:

> "MEF has a prefetcher."



It must be:

> MEF starts memory prediction substantially earlier and carries the prediction all the way into execution placement and uOP formation.



That distinction is much stronger.

Conceptually:

Kunminghu-like:

execute memory instruction
        ↓
observe address/access
        ↓
train/prefetch future memory


Proposed MEF:

fetch future memory instruction
        ↓
predict its address
        ↓
prepare translation/cache/data placement
        ↓
decode/rename/fuse instruction
        ↓
route execution toward predicted data
        ↓
validate prediction

That's a fundamentally different pipeline organization.

29. There is one security issue we should design in from day one

A wrong-path load prediction can change cache state.

That's a potential speculative side channel.

Therefore MPP should never simply be:

any predicted address → cache

The request must carry:

ASID
privilege
speculation epoch
branch confidence
translation status
memory type

and MPP must never speculatively touch MMIO/device memory.

High-security mode could also restrict:

wrong-path preview → private Tile-L0 only

until branch resolution.

Only afterward promote the data into shared L1.

That's a very appealing solution because you already have private near-tile storage.

I would implement it progressively: first memory-intent detection and L1 prefetch; then Preview Tokens and Tile-L0 placement; then pre-rename fusion hints; then post-rename dataflow fusion; then store-ownership preparation; and only after all of that is stable, high-confidence early consumption of predicted load data.

The most important conceptual shift is that this no longer treats memory as something that happens after execution scheduling.

In this architecture:

\[
\boxed{\text{memory preparation begins at fetch}}
\]

while:

\[
\boxed{\text{architectural memory execution remains validated at the LSU/LSQ}}
\]

That separation lets you be extremely aggressive in performance optimization while preserving precise RISC-V behavior. Combined with your per-tile near-memory and dynamic execution placement, I think this Memory Preview Pipeline + Dynamic Dataflow Fusion is one of the best remaining opportunities for creating a genuine single-thread performance advantage over a conventional Kunminghu-style OoO backend, rather than merely getting higher GPU/vector throughput.
